**Status**: Proposed (this PR)
**Layer**: Cross-cutting (catalog governance) + user-facing navigation
**Owner**: Coder (for eaojnr)
**Date**: 2026-10-13

We should consider a more appropriate approach that avoids the repeat, or ensures that the file and folder naming is more clearer and obvious."

## 1. Background and Authority

The mv1 migration (CR-BP-mv1) established `processes:<level>-<domain>-<stage>-<hash>` as the canonical id pattern (IDM-001, enforced by `scripts/check_id_system.py`). The level token (`pc`, `group`, `process`, `activity`, `task`, `scope`) names the L0..L4 position. The hash is BASE32 (IDM-004). The id system is correct as a *machine* identifier - every record has a unique id, every cross-reference resolves, the validator suite is green.

The user-facing problem is not the id system itself; it is the **collision surface** between the id system and the *names* + the **folder layout** that users navigate:

- **22 names** appear under multiple ids in the live tree (live inventory 2026-10-13). All 22 are **cross-level** collisions (L0 cell name shared with the L1 group that operates the cell, or L0 with L2 for some A&O / E&O / F&A / S&D cells). The pattern is the containment tree speaking: the cell *and* the group inside the cell can have parallel names; the relationship is "this group operates this cell". **0 same-level** identity collisions exist; the existing IDM-001 validator catches those at record-content-write time. The new EID-001 (blocking) and EID-004 (advisory, informational) gates in this CR codify the distinction: same-level dups are defects; cross-level reuses are the containment tree.
- **Folder depth** is 4-5 levels for L4 records (`fa-retire/fa-retire-2ptdnw/fa-retire-wkbrsa/fa-retire-3g3m9u/fa-retire-confirm-q2xkf3/processes-task-fa-retire-confirm-q2xkf3.yaml`). The intermediate directory names encode the BASE32 hash of the parent, which is not human-meaningful. A user navigating to a Task must traverse four hash-named directories.
- **2,900 of 3,723 records (78%) are L4 Tasks** and the user has to descend into 4-5 dirs to find one. The path encodes the L0->L4 hash chain, which is correct for uniqueness but hostile to navigation.
- **49 cell-root records vs 3,674 nested records**: the 49 `processes:pc-*.yaml` files at cell root are structurally the L0 ProcessContext for each cell; the 3,674 nested records are L1-L4. The asymmetry of "L0 lives at the top, L1+ lives deep" is intentional (it follows the containment tree) but is not signposted in the path.

The id system is correct; the navigation surface is hostile. The user directive calls out both.

## 2. Diagnosis gate (CR-BP-117a, this PR)

The new `scripts/check_entity_identity.py` (gate [31], blocking) is the permanent audit surface. Four rules:

- **EID-001 (advisory, but treated as a defect in --strict mode)**: a record's `name` does not appear under any other id at the *same* level. Two records at L2 both named "Demand Operate" would be EID-001 findings. Live tree: **0 hits**.
- **EID-002 (advisory)**: every record's README references the canonical id token in its first line. Catches stale hand-edited READMEs that lose the id. Live tree: **0 hits** (all READMEs were regenerated by CR-BP-114).
- **EID-003 (advisory)**: every record's README body surfaces the level token explicitly (e.g. "required at the L2 level"). The lower-bar body-level check; CR-BP-117c raises the bar to an explicit Path section. Live tree: **0 hits**.
- **EID-004 (advisory, informational)**: cross-level name reuse is the containment tree speaking. Reported as an inventory entry so users see the collision surface at a glance. Live tree: **22 hits** (L0 cell / L1 group / L2 process sharing names per the containment tree).

The EID-004 inventory (the 22 collisions) is the substantive finding of this CR. They are not defects. The user-facing concern - "which record do I navigate to" - is real, and the fix lives in CR-BP-117c. The diagnosis is what EID-004 reports.

## 3. Id-convention rename candidate (CR-BP-117b)

The id system is correct at the machine layer. The user's directive mentions "repeat of entities with different IDs"  -  that's the level-collision reading of §2. The candidate fixes the level-collision at the id level too, in case EID-002's name-disambiguation alone is not enough.

**Candidate 1: namespace the level into the id-prefix**

Change `processes:pc-...` -> `processes:cell-...` (and `group-` -> `group-`, `process-` -> `l2-process-`, `activity-` -> `l3-activity-`, `task-` -> `l4-task-`, `scope-` -> `scope-`). Cost: ~3,723 id rewrites; ~3,723 record files; ~3,723 record READMEs; all cross-references; all `migration-id-map.yaml` entries; the IDM-001 regex; the IDM-002..007 pattern variants; every gate that pattern-matches ids.

**Candidate 2: drop the level token from the id and rely on the name + level-aware README**

Keep `processes:<dom>-<stage>-<hash>` (no `pc-` / `group-` / etc. token). The level is recovered by the *containment path* (cell-root vs nested deeper) and by the entity type field. The 2,900 Tasks would have id collisions with the 580 Activities at the same cell unless the BASE32 hash is drawn from a level-distinct namespace, which it is not. So this candidate requires regenerating the BASE32 hash per level  -  same scope as Candidate 1 minus the rename, but with a hash-regen step that has higher risk of unintended collisions.

**Candidate 3: keep the id, change the user-facing surface only**

This is the EID-002 + EID-003 path: every record's README includes the level token in the displayed name and a level-aware path in the navigation header. No id changes, no migration, no cross-reference rewrites. The diagnosis gate (§2) reports the level-collisions as advisory findings, not as blockers.

**Recommendation**: **Candidate 3**. The id system is correct and is the source of truth for cross-references; rewriting it is a much larger surface than the user-facing problem requires. The level-collision at the name layer is fixable at the README layer, and the existing IDM-001..007 gates already enforce the machine layer. A separate CR is warranted only if the user concludes after the EID-002/003 landing that the id token still reads as a navigation problem.

The id-convention rename (Candidate 1 or 2) is a 6-8 week scope if it lands; the README-disambiguation (Candidate 3) is a 1-week scope and addresses the user-facing problem directly. Path B in the discussion thread (rename) and Path C (disambiguate at the surface) both have a place, but Path C first is the right sequencing.

## 4. Folder/Path clarity (CR-BP-117c, landed)

The folder layout today is:

```
entities/v1-alpha/
  <cell-slug>/                          # e.g. fa-retire
    README.md                           # cell root
    <dom-hash>/                         # e.g. fa-retire-2ptdnw
      <stage-hash>/                     # e.g. fa-retire-wkbrsa
        <self-hash>/                    # e.g. fa-retire-3g3m9u
          <task-slug>/                  # e.g. fa-retire-confirm-q2xkf3
            README.md
            processes-task-<...>.yaml
```

The intermediate hash directories carry no human-meaningful name; they exist for uniqueness. The user reads the path and sees four hash strings before reaching the record. Three concrete clarity moves:

**C-1: Level-named intermediate dirs (when unambiguous)**. Where the level is unambiguous at that depth, the directory carries the level's name. For example, a Task at the L4 dir is at the deepest level; the cell's name is already at `fa-retire/` so the next dir is the *Group* (L1), then the *Process* (L2), then the *Activity* (L3), then the *Task* (L4). The path becomes:

```
fa-retire/
  Conclude-Regulated-Run-Off/             # group (L1)
    Wind-Down-Liabilities/                 # process (L2)
      Settle-Final-Claim/                  # activity (L3)
        Confirm-Finality/                  # task (L4) - dir name matches the record name
          processes-task-fa-retire-confirm-q2xkf3.yaml
```

The hash stays in the filename. Directory names are kebab-cased record names. A name collision between two records at the same level (the EID-001 same-level case) disambiguates with the hash suffix: `Conclude-Regulated-Run-Off-2ptdnw/`.

**C-2: Symbolic links from the canonical path to the human-friendly path** (if we keep the hash-dir layout as ground truth). Symlinks are an opt-in tooling convenience, not a required change. Useful for users who want the human path but live in tools that expect the canonical path.

**C-3: A `tree --noreport` cheatsheet per cell in the cell-root README**. The cell-root README's "Path" section gains a "Path scheme" subsection that shows the human-friendly path for the L2/L3/L4 records in that cell, indexed by the L0 cell name. Users see the path before they navigate.

### 4.1 CR-BP-117c execution record (2026-10-13)

**C-1 landed**: `scripts/rename_dirs_human_names.py` renamed all 3,674 record directories (49 L1 groups, 145 L2 processes, 580 L3 activities, 2,900 L4 tasks) from `<cell>-<hash>` to the kebab-cased record name via `git mv`, bottom-up, zero collision fallbacks (the EID-001 same-level uniqueness invariant made collisions unreachable). The transform is `re.sub(r'[^A-Za-z0-9]+', '-', name).strip('-')`; 14 names with commas/parens/slashes collapsed cleanly (e.g. "Screen Candidates Against Sanctions / AML / FCRA / ADA" -> `Screen-Candidates-Against-Sanctions-AML-FCRA-ADA`). Gate safety verified before the rename: IDM-005 constrains filename + cell segment + depth only; READMEs embed no dir paths. Post-rename fixes: CATALOG.yaml regenerated (3,877 path entries), 2 doc references in `docs/examples/manage-customer-relationship.md` updated to the new paths. The cell dirs themselves (`fa-retire/` etc.) keep their `<domain>-<stage>` slugs by design.

**C-2 not landed** (per CR opt-in language): symlinks are unnecessary once C-1 makes the canonical path itself human-readable.

**C-3 landed**: `scripts/generate_readmes.py` gained a `path-scheme` section ("## 13. Path Scheme") for L0 ProcessContext READMEs, rendering the cell's directory tree with level labels derived from the record filename token. 49 cell-root READMEs regenerated; the other 3,674 record READMEs are byte-identical (RDM gate confirms). New helper `_cell_of_id` extracts the cell slug from a canonical id. New test module `tests/test_folder_path_clarity.py` (12 tests): kebab transform including the 14 special-char names, plan shape + collision fallback + deepest-first ordering on fixture trees, path-scheme tree render + malformed-id fallback, live invariant that no strict-BASE32 hash dirs remain below cell level.

## 6. NOT-List

- No id-system rewrite in this CR. The id-convention rename candidate is a follow-on if the EID-002/003 landing is insufficient.
- No entity-content changes. Records are touched only at the README rendering layer and the folder layout (Candidate 3 + C-1 path).
- No backfill of names. The 22 level-collision names are a *finding*, not a *defect*; the names are the containment-tree speaking. The fix is to surface the level in the user-facing display, not to rename records.
- No cross-repo scope. Sibling repos use the same id system; this is in-catalog work.

## 8. Result

The id system remains the source of truth; the user-facing surface gains a level-aware display (EID-002), a level-aware navigation header (EID-003), and a permanent gate that audits both. The folder layout becomes human-navigable (C-1) with the hash-names moved from directory names to filename suffixes. The 22 level-collisions are no longer ambiguous in the surface users actually see.
